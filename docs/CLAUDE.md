# AgentFront — Merchant Agent-Readiness Engine

Razorpay AI Buildathon 2026, Track 1 (AI Growth & Agentic Commerce).
Solo build. Deadline: 5 September 2026.

---

## Thesis

Agent commerce rails are being solved (NPCI UAP, Google AP2, ACP, x402).
**Merchants are not.** Real catalogs are prose written for human eyes —
inconsistent attributes, missing fields, no compatibility data. An AI buyer
cannot reliably transact against that.

AgentFront ingests a merchant's existing messy catalog and **generates** their
complete agent commerce surface: structured attributes, a verified
compatibility graph, MCP tool endpoints, an AP2-aligned Cart Mandate endpoint,
offer policies, and a gated payment path on Razorpay test mode.

**We are not building one agent-ready merchant. We are building the engine that
makes any merchant agent-ready.**

---

## Non-negotiable architectural rules

1. **The LLM does hard inference. Deterministic code does money, and verifies
   every LLM claim before it can affect a transaction.**
2. **No LLM imports in `surface/gate.py`, `surface/mandate.py`, or
   `pipeline/verify.py`.** This is enforced literally and is visible in the
   file tree. It is a load-bearing claim in the pitch.
3. **Fail closed, never open.** Any uncertainty → refuse or quarantine.
   Never guess about money or about a published attribute.
4. **No silent retries, ever.** Every retry is an explicitly logged decision
   with a reason code.
5. **Never hand-roll crypto or the MCP protocol.** Use PyNaCl (Ed25519) and the
   official MCP Python SDK.
6. **Refusals are logged as richly as successes.**

## Repo layout

```
/pipeline/          ← the AI core
  extract.py        attribute extraction + per-attribute confidence
  canonical.py      value normalization (USB C / Type-C / usb-c → enum)
  compat.py         LLM PROPOSES compatibility edges
  verify.py         code VERIFIES proposals   ← NO LLM IMPORTS
  quarantine.py     low-confidence SKUs are not published
/surface/           ← generated per merchant
  mcp_server.py     search / detail / offers / substitutes / status
  mandate.py        AP2 intent verify + cart mandate issue  ← NO LLM IMPORTS
  gate.py           ALLOW / REFUSE(code) / ESCALATE         ← NO LLM IMPORTS
  idempotency.py    Redis, keyed on hash(intent_mandate_id + cart_hash)
  refusal.py        structured refusal taxonomy
  payments.py       Razorpay test mode
/eval/
  ground_truth/     hand-labelled, held-out, NEVER tuned against
  extraction_eval.py    precision / recall / F1 per attribute
  growth_ab.py          before/after harness  ← the headline result
  adversarial/          independently generated attacks
/data/
  raw/              real messy catalog (public dataset)
/api/  /frontend/  /docs/
```

## AP2 role

We are **the merchant side**. AP2 chains Intent Mandate (user delegates
authority with price cap, category, expiry) → Cart Mandate (binds SKUs, price,
total to that intent) → Payment Mandate (what the network sees).

A merchant integrates AP2 by exposing a **Cart Mandate endpoint**. That is our
job. The buyer agent's Intent Mandate is **untrusted input** and is verified:
signature, expiry, price ceiling, category scope, nonce replay.

## The four growth metrics (this is a GROWTH track)

Same buyer agent, same intents, run twice — against the raw catalog (A) and the
generated surface (B):

| Metric | Why it is growth |
|---|---|
| Agent Completion Rate | sales lost when an agent gives up |
| Wrong-Item Rate | returns/chargebacks destroy merchant margin |
| Agent Basket Value | verified compatible bundles |
| Out-of-Stock Recovery | revenue saved from a dead end |

**If a feature does not eventually feed one of these numbers, it is out of
scope.**

## Evaluation integrity rules

- Ground-truth labels are **hand-written by the human, before the pipeline
  runs, from raw text only**. Never generated by a model. Never revised after
  seeing pipeline output.
- Adversarial attacks are generated by a **different model with no sight of our
  defenses or refusal taxonomy** — given only the API surface and the goal.
- **Report failures.** "14 attacks succeeded, here are the fixes" is stronger
  than a clean 100%, and doubles as the required "what broke" deliverable.
